The 8-Puzzle 🧩

Slide numbered tiles around a 3×3 grid until they land in order. Sounds simple — but finding the shortest path to the goal is a real search problem that AI textbooks love. Let's play, peek under the hood, and build it ourselves!

😃 What exactly is the 8-Puzzle?

You have a 3×3 board with 8 numbered tiles and one empty space. You can slide any tile that's next to the empty space into it. The goal: reach a target arrangement (usually 1→8 in order) starting from a shuffled one.

It's small enough to reason about, but big enough (181,440 reachable arrangements) that "just try everything" gets expensive — perfect for teaching search algorithms like BFS, A*, and Branch & Bound.

🌳 "Show me all the possibilities"

From any arrangement, the blank tile can usually move in 2–4 directions — each move branches into a new state. That branching, repeated over and over, is called the state space. Below is a real slice of it: the root state and every state reachable in 1 and 2 moves.

Notice states can even reconnect (moving right then left just undoes itself) — that's why we need a visited set, coming up next. Zoomed out, the entire 8-puzzle has 9!/2 = 181,440 reachable states — far too many to draw, which is exactly why smart search (not brute force drawing) is the answer.

🧠 The algorithm, step by step

Click a step to expand it. This is the classic A\* search (a smarter Branch & Bound) used to solve the 8-puzzle optimally.

  • Represent each board as a state (a list of 9 numbers, 0 = blank).

    e.g. [1,2,3,4,5,6,7,0,8] means the blank sits in position 7 (0-indexed).

  • Define a cost function f(n) = g(n) + h(n).

    g(n) = moves taken so far. h(n) = heuristic estimate to the goal — usually "Manhattan distance": sum of how far each tile is from its goal position.

  • Put the start state into a priority queue, ordered by lowest f(n).

    Lower f(n) = "looks more promising" — explore those first.

  • Pop the most promising state. If it's the goal — done! Return the path.

    We reconstruct the path by remembering each state's parent.

  • Otherwise, generate its neighbors (slide blank up/down/left/right).

    Skip moves that would push the blank off the board.

  • Skip any neighbor already in the visited set; push new ones into the queue with updated f(n).

    This avoids infinite loops and re-exploring the same board twice.

  • Repeat steps 4–6 until the goal pops out (or queue empties = unsolvable).

    Because we always expand the lowest f(n) first, the first time we pop the goal, it's guaranteed optimal (fewest moves).

📦 Which data structures — and why

⛰️

Priority Queue (min-heap)

Holds all "discovered but not yet expanded" states, always giving you the one with the lowest f(n) = g+h next. Without it you'd have to scan every waiting state each time — a heap does it in O(log n) instead of O(n).

🕵️

Hash Set (visited)

Stores boards we've already expanded (as a string key like "1,2,3,4,5,6,7,0,8"). Lookup is O(1), which is what stops the search from looping forever between two boards that just undo each other's move.

🧵

Parent map / linked path

Every time we discover a new state, we record "came from this state, via this move." When we hit the goal we just walk this chain backwards — that's how we recover the actual solution, not just its length.

🔢

Plain array / tuple (the state)

The board itself is just a flat array of 9 numbers. Simple, hashable (great for the visited set), and cheap to copy when generating neighbors.

💡 Fun fact: if you swap the priority queue for a plain FIFO queue and drop the heuristic, you get plain BFS — still optimal, just slower because it explores blindly instead of "toward" the goal.

💻 Language: Python 🐍 — build-it-yourself roadmap

Why Python: heapq gives you a priority queue for free, and tuples hash cleanly for a visited-set. (Java works too — PriorityQueue<> + HashSet<String> — just more typing.)

The Water Jug Problem 🪣

You've got a 4-litre jug and a 3-litre jug, no measuring marks. Can you measure out exactly 2 litres? This tiny puzzle is a favourite for teaching state-space search because you can hold the whole problem in your head — and on one screen.

😃 What exactly is it?

Two jugs, capacities 4L and 3L. Allowed moves: fill a jug fully, empty a jug fully, or pour one jug into the other until either the source is empty or the destination is full. Starting from (0, 0), reach a state where one jug holds exactly the target amount (e.g. 2L).

Jug A · 4L
Jug B · 3L

It looks trivial with two jugs, but it's a real illustration of state-space search: each (amount-in-A, amount-in-B) pair is a "state," and each fill/empty/pour is an "edge" to a new state — exactly the same idea as the 8-puzzle, just small enough to draw the whole map.

🕸️ Every possible state, mapped

Unlike the 8-puzzle, the water jug's whole universe is tiny: only 5 × 4 = 20 possible (A, B) states. Here they all are — the ones actually reachable from (0,0) light up as our BFS search "discovers" them, and the target(s) pulse gold.

🧠 The algorithm, step by step

Click a step to expand it. Because the state space is so small, plain BFS (breadth-first search) already finds the shortest sequence of moves.

  • Represent a state as a pair (a, b) — litres currently in Jug A and Jug B.

    Start state: (0, 0).

  • Put the start state into a FIFO queue, and mark it visited.

    FIFO = first-in-first-out, so we always explore in "distance order" from the start.

  • Pop the front state. If a==target or b==target, stop — success!

    Reconstruct the path from the parent map.

  • Otherwise generate all 6 possible next states: fillA, fillB, emptyA, emptyB, pourA→B, pourB→A.

    Pouring math: pour amount = min(source amount, space left in destination).

  • For each next state not yet visited: mark visited, record its parent, and enqueue it.

    This guarantees we never re-explore a state and never loop forever.

  • Repeat steps 3–5 until target is found or the queue is empty (no solution).

    With capacities 4 & 3 and target 2, a solution always exists here — try target 5 to see "no solution" instead!

📦 Which data structures — and why

🚋

Queue (FIFO)

BFS explores level-by-level — all 1-move states, then all 2-move states, etc. A queue naturally preserves that order, which is exactly what guarantees the first time we see the target, it's reached in the fewest moves.

🕵️

Visited set

Stores every (a,b) pair we've already queued, so we don't loop between the same two or three states forever (e.g. fill then empty then fill again).

🧵

Parent map

Same trick as the 8-puzzle: remember which state led to which, so once we hit the target we can walk backwards and print the actual move sequence.

🔢

Tuple (the state)

(a, b) as a simple tuple — small, hashable, easy to put straight into a Python set or a Java HashSet<String>.

💻 Language: Python 🐍 — build-it-yourself roadmap

Why Python: collections.deque is an O(1) queue out of the box, and tuples slot straight into a set. (Java: LinkedList<> as your Queue<int[]> + a HashSet<String> — works, just chattier.)

Wire up the BFS search
